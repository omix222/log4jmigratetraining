なぜ log4j 1.x から移行するのか

🚨
log4j 1.x は 2015 年 8 月に EOL（End of Life）

CVE-2019-17571 を含む複数の脆弱性が修正されないまま放置されています。プロダクション環境での使用は危険です。

log4j 2.x の主な改善点

機能log4j 1.xlog4j 2.x
パラメータ化ログ文字列結合 / isDebugEnabled() 必須{} プレースホルダーで遅延評価
非同期ロギングなしAsyncLogger (LMAX Disruptor)・高スループット
設定リロード不可monitorInterval で無停止リロード
構造化ログなしMapMessage・JsonTemplateLayout
Lookupなし${env:VAR}・${ctx:key} 等
フィルタ限定的Marker・Threshold・Regex フィルタ等
セキュリティ脆弱性あり (EOL)積極的にメンテされ CVE 対応

1
log4j 1.x の基本を理解する

まず移行元の log4j 1.x コードを理解します。移行後に「何が変わったのか」を対比するための基準点です。

Logger の取得と基本的な使い方

import org.apache.log4j.Logger;
import org.apache.log4j.MDC;

public class OrderService {

    // log4j 1.x: Logger.getLogger(Class) で取得
    private static final Logger logger = Logger.getLogger(OrderService.class);

    public void placeOrder(String orderId, String customerId, int amount) {
        // MDC: リクエストスコープの情報を全ログに付加
        MDC.put("orderId", orderId);
        MDC.put("customerId", customerId);

        logger.info("注文処理を開始します");

        // ⚠ 1.x では {} プレースホルダーが使えない
        // → 文字列結合 または isXxxEnabled() ガードが必要
        if (logger.isDebugEnabled()) {
            logger.debug("注文詳細: orderId=" + orderId + ", amount=" + amount);
        }

        try {
            validateOrder(orderId, amount);
            logger.info("注文が正常に完了しました");
        } catch (Exception e) {
            logger.error("注文処理中にエラーが発生", e);
        } finally {
            // ⚠ スレッドプール汚染防止のため必ずクリアすること
            MDC.remove("orderId");
            MDC.remove("customerId");
        }
    }
}

FATAL レベルと PaymentService

public class PaymentService {
    private static final Logger logger = Logger.getLogger(PaymentService.class);

    public boolean charge(String paymentId, int amount) {
        if (amount > 1_000_000) {
            // log4j 1.x の FATAL — 「アプリ続行不可」を示す
            // 2.x 移行後は ERROR で代替するのが推奨
            logger.fatal("決済上限超過。不正な取引の可能性: amount=" + amount);
            return false;
        }
        // ...
    }
}

log4j.properties の書き方

# ルートロガー: DEBUG 以上を Console と File へ出力
log4j.rootLogger=DEBUG, Console, File

# ConsoleAppender の設定
log4j.appender.Console=org.apache.log4j.ConsoleAppender
log4j.appender.Console.Target=System.out
log4j.appender.Console.layout=org.apache.log4j.PatternLayout
# %X{key} で MDC の値を出力できる
log4j.appender.Console.layout.ConversionPattern=%d{yyyy-MM-dd HH:mm:ss.SSS} [%t] %-5p %c{1} [orderId=%X{orderId}] - %m%n

# FileAppender の設定
log4j.appender.File=org.apache.log4j.FileAppender
log4j.appender.File.File=target/step1-log4j1.log
log4j.appender.File.Append=false
log4j.appender.File.layout=org.apache.log4j.PatternLayout
log4j.appender.File.layout.ConversionPattern=%d{ISO8601} [%t] %-5p %c - %m%n

# 特定パッケージのレベルを上書き
log4j.logger.com.example=DEBUG
⚠️
1.x の代表的な問題点

① isDebugEnabled() を忘れると DEBUG 無効時も文字列結合が実行されムダな CPU コストがかかる。② MDC をクリアし忘れるとスレッドプール環境で前のリクエストの情報が次のリクエストに混入する。

実行コマンド

mvn -pl step1-log4j1 exec:java

2
ブリッジ移行（コード変更ゼロ）

Java ソースを一切変えずに、バックエンドを log4j 2.x に切り替えます。リスクを最小化した第一歩として有効な手法です。

pom.xml の変更だけで移行

⚠ Step 1 — log4j 1.x
<dependency>
  <groupId>log4j</groupId>
  <artifactId>log4j</artifactId>
  <version>1.2.17</version>
</dependency>
✓ Step 2 — ブリッジ
<dependency>
  <groupId>org.apache.logging.log4j</groupId>
  <artifactId>log4j-1.2-api</artifactId>
</dependency>
<dependency>
  <groupId>org.apache.logging.log4j</groupId>
  <artifactId>log4j-core</artifactId>
</dependency>
🚨
log4j.properties は自動的に無視される

log4j 2.x バックエンドは log4j.properties を読み込みません。必ず log4j2.xml（または log4j2.json）を作成してください。

log4j2.xml の作成（新規ファイル）

<?xml version="1.0" encoding="UTF-8"?>
<Configuration status="WARN" monitorInterval="30">

  <Appenders>
    <Console name="Console" target="SYSTEM_OUT">
      <PatternLayout pattern="%d{HH:mm:ss} [%t] %-5level %logger{1} [%X{orderId}] - %msg%n"/>
    </Console>

    <!-- RollingFile: 1.x の FileAppender より高機能な後継 -->
    <RollingFile name="RollingFile"
                 fileName="target/app.log"
                 filePattern="target/app-%d{yyyy-MM-dd}-%i.log.gz">
      <JsonTemplateLayout/>   <!-- 構造化 JSON ログ -->
      <Policies>
        <SizeBasedTriggeringPolicy size="10 MB"/>
        <TimeBasedTriggeringPolicy interval="1"/>
      </Policies>
      <DefaultRolloverStrategy max="7"/>
    </RollingFile>
  </Appenders>

  <Loggers>
    <Logger name="com.example" level="DEBUG" additivity="false">
      <AppenderRef ref="Console"/>
      <AppenderRef ref="RollingFile"/>
    </Logger>
    <Root level="WARN">
      <AppenderRef ref="Console"/>
    </Root>
  </Loggers>

</Configuration>
💡
JsonTemplateLayout を使う場合は追加依存が必要

log4j-core には含まれていません。log4j-layout-template-json を依存に追加してください。

実行コマンド

mvn -pl step2-bridge exec:java

3
log4j 2.x ネイティブ API への完全移行

コードを log4j 2.x の API に書き直します。パフォーマンスが向上し、新機能をフル活用できます。

Java コードの変更点

⚠ Step 1 — log4j 1.x
import org.apache.log4j.Logger;
import org.apache.log4j.MDC;

private static final Logger logger =
    Logger.getLogger(OrderService.class);

MDC.put("orderId", orderId);

// ガードが必要
if (logger.isDebugEnabled()) {
    logger.debug("orderId=" + orderId);
}
✓ Step 3 — log4j 2.x
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;
import org.apache.logging.log4j.ThreadContext;

private static final Logger logger =
    LogManager.getLogger(OrderService.class);

ThreadContext.put("orderId", orderId);

// {} プレースホルダー — ガード不要
logger.debug("orderId={}", orderId);

新機能: ラムダによる遅延評価

// DEBUG が無効なら getDetailedInfo() は呼ばれない (コスト不要)
logger.info(() -> "決済成功: 詳細=" + getDetailedInfo(paymentId));

新機能: MapMessage で構造化ログ

import org.apache.logging.log4j.message.MapMessage;

MapMessage<?, ?> msg = new MapMessage<>()
        .with("event",      "order.placed")
        .with("orderId",    orderId)
        .with("customerId", customerId)
        .with("amount",     String.valueOf(amount));
logger.info(msg);
// JsonTemplateLayout と組み合わせると JSON フィールドとして出力される

log4j2.xml の新機能

<!-- monitorInterval: 設定ファイルを無停止でリロード (秒単位) -->
<Configuration status="WARN" monitorInterval="30">

  <Properties>
    <!-- 設定内で変数として再利用できる -->
    <Property name="LOG_DIR">target</Property>
  </Properties>

  <Appenders>
    <!-- JsonTemplateLayout: Elasticsearch / Splunk に流しやすい構造化ログ -->
    <RollingFile name="JsonFile"
                 fileName="${LOG_DIR}/app.jsonl"
                 filePattern="${LOG_DIR}/app-%d{yyyy-MM-dd}-%i.jsonl.gz">
      <JsonTemplateLayout/>
      <Policies>
        <SizeBasedTriggeringPolicy size="10 MB"/>
      </Policies>
    </RollingFile>

    <!-- 非同期 Appender: ロギングを別スレッドに委譲 -->
    <Async name="AsyncConsole">
      <AppenderRef ref="Console"/>
    </Async>
  </Appenders>
</Configuration>

実行コマンド

mvn -pl step3-log4j2-native exec:java

4
SLF4J ファサードでベストプラクティス

SLF4J (Simple Logging Facade for Java) はロギング実装を抽象化するファサードです。アプリケーションコードを特定の実装ライブラリ（log4j2/logback）に依存させない業界標準のベストプラクティスです。

pom.xml の依存関係

<!-- コンパイル依存: API のみ —— 実装を意識しないコードを書く -->
<dependency>
  <groupId>org.slf4j</groupId>
  <artifactId>slf4j-api</artifactId>
</dependency>

<!-- ランタイム依存: SLF4J → log4j2 へのブリッジ -->
<dependency>
  <groupId>org.apache.logging.log4j</groupId>
  <!-- SLF4J 2.x 用: slf4j2-impl。1.x 用の slf4j-impl と混同しないこと -->
  <artifactId>log4j-slf4j2-impl</artifactId>
  <scope>runtime</scope>
</dependency>

Java コードの変更点

⚠ Step 3 — log4j 2.x ネイティブ
import org.apache.logging.log4j.LogManager;
import org.apache.logging.log4j.Logger;
import org.apache.logging.log4j.ThreadContext;

private static final Logger logger =
    LogManager.getLogger(OrderService.class);

ThreadContext.put("key", value);
ThreadContext.remove("key");
✓ Step 4 — SLF4J
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

private static final Logger logger =
    LoggerFactory.getLogger(OrderService.class);

MDC.put("key", value);
MDC.remove("key");

SLF4J 2.x の Fluent API

// atInfo() + addKeyValue() で構造化ログを簡潔に書ける
logger.atInfo()
      .addKeyValue("event",      "order.placed")
      .addKeyValue("orderId",    orderId)
      .addKeyValue("customerId", customerId)
      .addKeyValue("amount",     amount)
      .log("注文を受け付けました");
⚠️
SLF4J バージョンとブリッジ名の対応を間違えないこと

SLF4J 2.x → log4j-slf4j2-impl　　SLF4J 1.x → log4j-slf4j-impl（数字の位置が違う）。混在させると SLF4J: No SLF4J providers were found. エラーになります。

💡
SLF4J を選ぶ理由

ライブラリ開発者は SLF4J を使うべきです。アプリ開発者もロギング実装の選択を pom.xml 1 行で切り替えられるため、将来 logback へ移行する場合もコード変更が不要です。

実行コマンド

mvn -pl step4-slf4j exec:java

5
OpenRewrite で Java コードを自動変換

OpenRewrite は AST（抽象構文木）ベースのリファクタリングツールです。Java ソースコードを機械的に変換するレシピを適用します。

pom.xml の設定

<plugin>
  <groupId>org.openrewrite.maven</groupId>
  <artifactId>rewrite-maven-plugin</artifactId>
  <version>5.42.0</version>
  <configuration>
    <activeRecipes>
      <!-- log4j 1.x → log4j 2.x に変換するレシピ -->
      <recipe>org.openrewrite.java.logging.log4j.Log4j1ToLog4j2</recipe>
      <!-- SLF4J に移行したい場合はこちらに変更: -->
      <!-- <recipe>org.openrewrite.java.logging.slf4j.Log4j1ToSlf4j</recipe> -->
    </activeRecipes>
  </configuration>
  <dependencies>
    <dependency>
      <groupId>org.openrewrite.recipe</groupId>
      <artifactId>rewrite-logging-frameworks</artifactId>
      <version>2.14.0</version>
    </dependency>
  </dependencies>
</plugin>

レシピが変換する内容

変換前 (log4j 1.x)変換後 (log4j 2.x)
import org.apache.log4j.Loggerimport org.apache.logging.log4j.Logger
Logger.getLogger(Clazz)LogManager.getLogger(Clazz)
import org.apache.log4j.MDCimport org.apache.logging.log4j.ThreadContext
MDC.put(k, v)ThreadContext.put(k, v)
MDC.remove(k)ThreadContext.remove(k)
isDebugEnabled() + "x=" + xlogger.debug("x={}", x)
log4j:log4j (pom.xml)log4j-api + log4j-core に置換

実行方法

# JDK 21 以下が必要！ (Java 25 では NoClassDefFoundError が発生する)
export JAVA_HOME=$(/usr/libexec/java_home -v 21)

# ドライラン: ファイルを変更せずに差分を確認
mvn -pl step5-openrewrite rewrite:dryRun
cat step5-openrewrite/target/rewrite/rewrite.patch

# 実際に適用 (ファイルが書き換えられる)
mvn -pl step5-openrewrite rewrite:run
🚨
Java 25 では Java ソース変換が失敗する

OpenRewrite は内部で com.sun.tools.javac.* を使いますが、このクラスは Java 25 で削除されています。JDK 21 以下で実行してください。pom.xml の依存更新は Java 25 でも動作します。

6
Log4j1ConfigurationConverter で設定ファイルを変換

log4j-1.2-api に内包される公式ツール。log4j.properties ファイルを log4j2.xml に自動変換します。

使い方

# Maven exec プラグイン経由で実行
mvn -pl step6-config-converter exec:java@convert-properties

# 出力を確認
cat step6-config-converter/target/log4j2-from-properties.xml

変換元 log4j.properties（抜粋）

# ルートロガー
log4j.rootLogger=INFO, Console, RollingFile

# ConsoleAppender
log4j.appender.Console=org.apache.log4j.ConsoleAppender
log4j.appender.Console.layout=org.apache.log4j.PatternLayout
log4j.appender.Console.layout.ConversionPattern=%d{HH:mm:ss.SSS} [%t] %-5p %c{1} [%X{orderId}] - %m%n

# RollingFileAppender
log4j.appender.RollingFile=org.apache.log4j.RollingFileAppender
log4j.appender.RollingFile.MaxFileSize=10MB
log4j.appender.RollingFile.MaxBackupIndex=5

# アプリロガー (additivity=false)
log4j.logger.com.example=DEBUG, Console, RollingFile
log4j.additivity.com.example=false

変換後の log4j2.xml（抜粋）

<Configuration>
  <Appenders>
    <Console name="Console" target="SYSTEM_OUT">
      <!-- ⚠ %-5v1Level は誤変換 → %-5level に手動修正が必要 -->
      <!-- ⚠ %properties{orderId} も誤変換 → %X{orderId} に修正 -->
      <PatternLayout pattern="%d{HH:mm:ss.SSS} [%t] %-5v1Level %c{1} [%properties{orderId}] - %m%n"/>
    </Console>
  </Appenders>
</Configuration>

変換後に手動確認が必要な箇所

⚠️
自動変換後の必須チェックリスト

① %-5v1Level → %-5level に修正（パターン文字の誤変換）
② %properties{key} → %X{key} に修正（MDC 出力の誤変換）
③ additivity="false" の欠落がないか確認
④ DailyRollingFileAppender は TimeBasedTriggeringPolicy に変換されるが filePattern を要確認

🚨
XML 形式 (log4j.xml) は変換できない

このツールは log4j.properties 形式のみ対応しています。DOCTYPE ベースの XML は正しく読み込まれません。XML 形式の場合は Step 7 の farnetto/log4jconverter を使用してください。

7
farnetto/log4jconverter で XML 設定ファイルを変換

Step 6 が対応できない XML 形式（<!DOCTYPE> ベース）の log4j.xml を変換するコミュニティ製ツールです。JAXB で XML をパースし FreeMarker テンプレートで log4j2.xml を生成します。

よくある落とし穴と対処法

1. log4j.properties が無視される

🚨
症状: ブリッジ移行後にログが出なくなった

log4j 2.x バックエンドは log4j.properties を読みません。クラスパスに log4j2.xml（または log4j2.json）が必要です。log4j-1.2-api ブリッジ経由でも同様です。

2. FATAL の扱い

⚠ log4j 1.x / 2.x
logger.fatal("致命的エラー");
// SLF4J には FATAL がない → コンパイルエラー
✓ SLF4J 移行後
logger.error("致命的エラー");
// FATAL → ERROR で代替

3. MDC のクリア忘れ

// ✓ スレッドプール環境では必ず finally でクリアする
MDC.put("orderId", orderId);
try {
    // 処理
} finally {
    MDC.remove("orderId");   // ← これがないと次のリクエストに混入
}

4. SLF4J ブリッジ名のバージョン混同

SLF4J バージョン正しいブリッジ間違い
SLF4J 2.x log4j-slf4j2-impl log4j-slf4j-impl
SLF4J 1.x log4j-slf4j-impl log4j-slf4j2-impl
ℹ️
エラーメッセージ: SLF4J: No SLF4J providers were found.

ブリッジのアーティファクト名とバージョンが一致していないときに発生します。mvn dependency:tree で両方が同時にクラスパスに存在していないか確認してください。

5. 依存の重複

<!-- ✗ log4j-1.2-api と log4j:log4j を同時に含めると競合 -->
<!-- ブリッジ移行後は log4j:log4j の除外を忘れずに -->
<dependency>
  <groupId>log4j</groupId>
  <artifactId>log4j</artifactId>
  <scope>compile</scope>  <!-- ← 削除する -->
</dependency>

6. OpenRewrite のバージョン整合

<!-- rewrite-maven-plugin の rewrite-core バージョンと -->
<!-- rewrite-logging-frameworks の rewrite-bom バージョンを一致させること -->
<!-- 不一致の場合: "Recipe validation error in ParameterizedLogging" -->
<version>5.42.0</version>        <!-- rewrite-maven-plugin -->
<version>2.14.0</version>        <!-- rewrite-logging-frameworks -->

API チートシート

Logger 取得

コード
1.x private static final Logger logger = Logger.getLogger(MyClass.class);
2.x private static final Logger logger = LogManager.getLogger(MyClass.class);
SLF4J private static final Logger logger = LoggerFactory.getLogger(MyClass.class);

ログ出力

パターンコード例
1.x 文字列結合 logger.debug("id=" + id + " amount=" + amt);
1.x isEnabledガード if (logger.isDebugEnabled()) { logger.debug("id=" + id); }
2.x {} プレースホルダー logger.debug("id={}, amount={}", id, amt);
2.x ラムダ遅延評価 logger.info(() -> "詳細=" + expensive());
2.x MapMessage logger.info(new MapMessage<>().with("k", v));
SLF4J {} プレースホルダー logger.debug("id={}, amount={}", id, amt);
SLF4J Fluent API logger.atInfo().addKeyValue("id", id).log("メッセージ");
